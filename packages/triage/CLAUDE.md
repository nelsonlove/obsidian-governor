# Vault Triage (plugin id `vault-triage`) — architecture & working notes for Claude Code

Inbox triage as its own Obsidian plugin: a read-only queue view and one guarded, dry-run-by-default disposition verb, published to the Governor host through `vault-mcp-api`. Extracted from the host at the suite split's S5 (`docs/suite-split-design.md` §6, "Triage | private operator | satellite"), following the `packages/quickadd-choices-compile` pilot and the `packages/skills` satellite. Package layout, build/test commands, and the extraction's four consequences are in `README.md`; the user-facing model is `docs/triage.md` at the repo root.

## Locked decisions (don't relitigate without reason)

- **The published tool names CHANGED, and that was a deliberate trade — this is the one thing to know before touching anything here.** `triage_queue` / `triage_dispose` are now `vault_triage_queue` / `vault_triage_dispose`. The host publishes an external tool as `<sanitized publisher id>_<bare name>`, so **the plugin id and the tool namespace are the same string**; `vault-triage` sanitizes to `vault_triage`. The alternative existed and was NOT taken: a plugin id of literally `triage` would have sanitized to `triage` and reproduced the shipped names exactly, the way `vault-skills` did for `vault_skills_*`. It was declined because the extraction was specified with the id `vault-triage`, which is the suite's naming convention (`vault-skills`, `vault-triage`), and because a bare `triage` is a very collision-prone id in a global Obsidian plugin namespace. The cost is real and should not be understated: the host's own locked decision says renaming shipped tool names breaks agent sessions for zero semantic gain, and these two were live. **If that trade is ever revisited, it is a one-line change** — `manifest.json`'s `id`, plus the strings in `tests/host-shim.mjs` and the settings tab's status line. Nothing else in the package encodes the prefix.

- **`triage_dispose`'s destination argument is `target_path`, not `target`, and it must stay a name the host's guard recognizes.** The host's `PATH_KEYS` are `path`, `from`, `to`, `target_path`, `template_path`, `subdir`, `file_path`, `output_folder`. While triage was a module, `target` being unrecognized was fine because the handler re-checked the COMPUTED destination itself with `ctx.visible`, wired from the host's guard settings. A satellite cannot reach those settings, so that check is dormant and the argument name is what the host has to scope by. Renaming it was the `to_address` / `displace_to_address` precedent applied in the direction that ADDS a check. Pinned by test (`publication: … what the host's guard can scope`), including that `target` does not come back.

- **Be precise about what the allowlist covers.** `path` and `target_path` are guard-checked. A declared row's CONFIGURED `destination`, used without a `target_path`, is not — it is not a call argument, so nothing the host sees names it. That is not a hole to paper over with a claim: the bound on that path is the human's `moveWhitelist` / `moveBlacklist`, enforced at plan time AND re-checked at apply against a fresh config read. The session allowlist scopes what the CALLER can name; a declared row's destination is the human's standing choice. Say it that way; do not write "every destination is allowlist-checked".

- **`ctx.visible` / `ctx.getSettings` are dormant seams, kept deliberately.** Nothing supplies them in the shipped configuration, exactly like the skills satellite's `preview` filter. Do not delete them: their tests supply them so they cannot rot, and a `vault-mcp-api` that can carry the caller's scope to a publisher (apiVersion 2) makes them live again with no code change.

- **Base-backed queues are unavailable, and copying the seam would be WRONG, not merely big.** `queryBaseRows` did not come with triage at S5; at S7 it MOVED with the bases surface into `packages/bases/src/tools.ts` (a move, no copy left behind — nothing in `packages/plugin/src` references it any more). Its capture drives a hidden Bases leaf — a GLOBAL resource guarded by a module-scoped serializer holding it to one capture at a time — so a second copy in a second plugin races the first over the one leaf. That is why the seam had to MOVE at S7 rather than be copied, and it is why a copy here would still be wrong: two plugins each holding a serializer over the one leaf is the same race whichever two plugins they are. The `baseQuery` ctx seam stays, unsupplied, and the base/queue forms refuse `bases_unavailable` through the branch that always covered a pre-Bases Obsidian. The `queues` config field is kept and its help text says it is inert. Callers wanting evaluated Base rows use the `vault-bases` satellite's `vault_bases_query` (the module's `base_query`, renamed by publication; `base_list` became `vault_bases_list`).

- **`executeQuickAddChoice` was PUBLISHED to `@vault-mcp/core`, never copied.** Its own header always said it exists so the two surfaces that drive a choice headlessly "cannot drift on how a choice is resolved and invoked" — and after S5 those two surfaces are in different plugins (the host's `obsidian_run_command`, and this plugin's declared `choice` rows). A copy would have reinstated exactly the drift it was written to prevent. Same reasoning as `isVisible` at S4.

- **`moveNote` in `obsidian-source.ts` IS a duplicate of the host's `moveOne`, and that one is unavoidable.** `moveOne` has three other host callers so it stays there, and it imports `obsidian`, so it cannot be published through `@vault-mcp/core`, which is obsidian-free by contract. What is shared is the RULE, not the function: never `app.vault.rename`, which moves the bytes and orphans every backlink. `tests/link-healing.test.mjs` pins it the same way the host does — the real adapter driven against a fake app whose `vault.rename` throws, plus a source scan over this package's own `src/**/*.ts` that is itself proven against a planted violation. If you add a second write path here, it goes in that test.

- **Handlers return plain data and THROW on refusal**, with a lowercase-snake `code` on the error; the host's `fail()` renders `Error [code]: message`. There is no `ok`/`fail`/`codedError` import here — those helpers are host-internal. **One envelope changed and only one:** the mid-sequence partial failure was `okError(...)` (ok's structure plus the error flag), which a published handler cannot produce. It now throws `dispose_partially_applied` carrying the facts in the message. The property kept is "a partial disposition is always NAMED"; the cost is the journal's `effects` field on that one path.

- **Re-apply every schema bound in the handler.** The SDK converts zod to JSON Schema and the host converts it back through a small subset (`src/mcp/json-schema-to-zod.ts`): `type`, `description` and string `enum` survive; `default`, `min`, `max`, `pattern` do NOT. The `limit` clamp and the `dry_run: true` default therefore run in the handler. This is the `vault_skills_release` semver bug, avoided rather than repeated — if you add a constrained argument, constrain it twice.

- **Config is read PER CALL, never captured.** `TriageToolsCtx.config` is a thunk. But the `disposition` ENUM and the tool DESCRIPTIONS are necessarily build-time snapshots of that config, because the host snapshots a published spec's schema — so `main.ts` **disposes and re-publishes on every settings write**. As a module the specs were rebuilt per connection; this restores that freshness at a finer granularity. Do not "simplify" `republish()` back into a single `this.register(publishTools(...))` in onload: a newly declared disposition row would become unreachable through the schema until an Obsidian reload.

- **NO ACCEPTANCE SEMANTICS ANYWHERE, and no disposition confers standing.** The built-ins are mechanical, reversible writes; a declared `choice` row runs a QuickAdd choice the HUMAN bound in config. The agent-facing surface is the disposition id only, so the host's `quickadd:*` / `js-engine:*` opaque-execution denies are not weakened — an agent picks from the human's menu and cannot name a macro. Every frontmatter patch re-runs `acceptForbiddenReason` from `@vault-mcp/core` before it is written, on top of config validation already refusing acceptance-carrying patches loudly. The deny CONSTANTS themselves are host code and are pinned exactly in the host's `tests/cli-policy.test.mjs`; this package pins its own half (a raw command id or bare choice name is not a disposition).

- **The disposition substrate comes from `@vault-mcp/core`.** `DispositionDescriptorShape`, `DispositionAuthority` and the three helpers were published there at S3 condition 9 precisely so triage could leave without the governance provider depending on it. The local `kernel/triage/dispositions.ts` re-export shim went away WITH the module — there is nothing left in the host to re-export to. The equivalence claim ("both instances behave identically through the shared helpers") is now pinned from both sides: the acceptance instance in the host's `tests/governance-dispositions.test.mjs`, the triage instance here.

- **The three built-in primitives are trash / move / stamp.** Anything describing "ten verbs" is pre-#241 and stale. Everything richer is a human-declared config row; the merged (built-in ∪ declared) table is a derived per-config view and is the single source for the tool enum, the tool description, and the docs.

## Build / test

- `npm run build` — esbuild, emits `main.js`. No assets, no defines: unlike the skills satellite there is nothing to embed.
- `npm test` — `pretest` builds `@vault-mcp/core`, then `tsc --noEmit && node --import tsx --test`. **The `pretest` is load-bearing, not tidiness:** the tests reach published core contracts through `packages/core/dist` — the COMPILED output. Without the rebuild you test the previous build's bytes.
- Install for testing: copy `main.js` + `manifest.json` into `<vault>/.obsidian/plugins/vault-triage/` and reload the plugin. During development add an empty `.hotreload` file in that directory so the hot-reload plugin picks up rebuilds — it belongs to the vault install, not to this repo.

## Headless testing

Everything except `src/obsidian-source.ts` and `src/settings-tab.ts` is unit-tested without Obsidian: the planner and the merged table are pure over their inputs, the tool handlers run over a fake `TriageSource`, the accept guard over plain objects, and the settings adoption over plain records. `tests/host-shim.mjs` reproduces the three things the host does to a published tool — the `<sanitized id>_<bare name>` naming, the `ok()`/`fail()` envelopes including the coded rendering, and the annotations it derives from an UNTRUSTED `readOnly` claim — so the tests assert the envelopes an agent actually sees rather than raw return values. It deliberately does NOT reproduce the F3 pathless-tool block or the path allowlist: those are host code with host tests, and a second copy could drift into asserting a posture the host does not enforce.

`src/obsidian-source.ts` IS reached headlessly, through `tests/obsidian-stub.mjs` (the host's `installObsidianStub` pattern), because "a move renames link-aware" is a property of the real adapter, not of a re-implementation. Use that sparingly; keep new logic on the Obsidian-free side of the line.
