# Vault Skills (plugin id `vault-skills`) — architecture & working notes for Claude Code

The skills compiler as its own Obsidian plugin: it compiles the vault's skill / agent / policy / command notes into a Claude Code plugin on disk, and publishes six MCP tools to the Governor host through `vault-mcp-api`. Extracted from the host at the suite split's S4 (`docs/suite-split-design.md` §6, "Skills compiler | private operator | satellite"), following the `packages/quickadd-choices-compile` pilot. Package layout, build/test commands, and the extraction's two consequences are in `README.md`; the user-facing model is `docs/skills.md` at the repo root.

## Locked decisions (don't relitigate without reason)

- **The six tool names are historical and do NOT change.** `vault_skills_validate`, `_tree`, `_preview`, `_export`, `_release`, `_mark`. Each spec in `src/tools.ts` carries only the BARE half (`validate`, …); the host publishes an external tool as `<sanitized publisher id>_<bare name>`, and `vault-skills` sanitizes to `vault_skills`, so the shipped spellings reproduce exactly. This is the host's own precedent for `governance_revisions` / `governance_submit_revision`: renaming shipped tool names breaks agent sessions for zero semantic gain. **A consequence to keep in mind: the plugin id and the tool namespace are the same string.** Renaming the plugin id renames every tool.

- **The compile is WHOLE-VAULT and stays that way.** Parent edges span the tree, so a partial compile produces a broken plugin. Everything that scopes or filters therefore acts on what is RETURNED, never on what is compiled.

- **The allowlist boundary is the HOST's, and it is stricter than the filter it replaced.** The in-tool visibility filter in `src/tools.ts`'s `preview` handler is retained in full and does nothing in the shipped configuration — nothing supplies `ctx.getSettings`, because a satellite cannot reach the host's guard settings, so it degrades through the same `!settings ||` branch it always had. What actually enforces: the host distrusts an external tool's `readOnlyHint: true` unless the publisher's RAW id is in its `trustedReadOnlyPlugins`, so all six register as MUTATING; and a mutating external tool whose arguments carry no recognized path key is BLOCKED OUTRIGHT while a path allowlist is active. Five of the six carry no path argument ⇒ refused wholesale. `mark` carries `path` ⇒ scoped normally. **Do not delete the dormant filter** — the assembled-body reasoning inside it (an entry's own source, everything it transcludes, AND every `type: policy` note injected into an agent; plus the `"(static)"` marker, which is not a vault path) was found by an independent review of a first fix that checked only the entry's own `from`, and it becomes live again when `vault-mcp-api` can carry the caller's scope to a publisher (an apiVersion-2 item). Its tests supply `getSettings` themselves so it cannot rot.

- **`isVisible` / `GuardSettings` come from `@vault-mcp/core`, never a local copy.** They were published there at this extraction precisely so the host's `guard.ts` and this plugin ask one question. A second copy of a guard predicate is the drift this repo has paid for twice.

- **`vault_skills_mark` runs the accept-forbidden guard before any write** (`guardSkillsMark` in `src/tools.ts`): it computes the frontmatter the mark WOULD land and runs `acceptTransitionReason` from `@vault-mcp/core` — the same predicate the fs and Obsidian write primitives use. A mark can never introduce or change an `accepted` / `accepted-by` / `accepted-on` field, or set `acceptance-status` to an accepted value; carrying an existing human-granted value forward unchanged is allowed. The GUI `mark` command routes through the identical function, so the human path is not a bypass. Extraction did not weaken this: the predicate is a published core contract. Pinned by `tests/skills-module.test.mjs` — including that a refusal blocks the WRITE, not just the response.

- **Handlers return plain data and THROW on refusal.** The host wraps a return value in `ok()` and a thrown error in `fail()`, so the envelopes agents see are unchanged from the folded era. There is no `ok`/`fail` import here; those helpers are host-internal.

- **Config is read PER CALL, never captured.** `SkillsToolsCtx.config` is a thunk. The host holds a spec snapshot per connection, so a captured config would freeze the settings tab's values at plugin load.

- **Settings adoption is one-shot and never writes the host.** See `src/settings.ts`. Three rules, each pinned: it never writes the host's settings (the host's copy stays and simply stops being read); it latches (`adoptedFromHost`), so a later host edit cannot reach back in; and this plugin's own values win, adoption only filling gaps. A host that is ABSENT adopts nothing and does NOT latch, so a standalone install keeps its one chance for later.

- **The plugin works with no host installed.** The pane, commands, ribbon and export-on-save are pure Obsidian plus the compiler core; only the tools go unpublished. `main.ts` wires the human surface BEFORE it publishes so the claim and the code agree (`publishTools` is internally defensive, which makes the ordering belt rather than fix — the pilot's reasoning).

- **The compiled edge model** (`src/kernel/`, #292). The compiled output is **FLAT** (`skills/<name>/SKILL.md`, `agents/<name>.md`; `genName` derives from the note's own name, not tree position), so every emitted skill is reachable by every emitted agent through the Skill tool. Consequences, all deliberate: **(1)** `parent:` is an organizational/provenance edge and is MULTI-VALUED — the FIRST parent is PRIMARY (tree edge, breadcrumb, `level`, ownership, reachability/cycle checks), the rest are recorded ATTACHMENTS with no effect on any compiled path; every named parent is still validated; `type: policy` keeps STRICT single-parent (its parent is a lineage edge, and a second would mean a second injection site). **(2)** The agent `skills:` frontmatter is PRELOAD, not permission — emitted from an OPT-IN per-skill `preload: true`, never from attachment alone; `preloadCap` (default 5) WARNS, never refuses. **(3)** `no-skills: true` on an AGENT compiles `disallowedTools: [Skill]` — `disallowedTools` rather than a `tools` allowlist is load-bearing, because it applies BEFORE `tools` resolves and so leaves the agent's other tools alone. The full reasoning is the decision-record bullet in `packages/plugin/CLAUDE.md` (kept there deliberately: that file is the record of what was decided, and the extraction did not re-decide it) and the user-facing form is `docs/skills.md`.

## Build / test

- `npm run build` — esbuild, emits `main.js`. The build embeds `assets/new-skill/SKILL.md` and `conventions.md` as the `__NEW_SKILL_MD__` / `__NEW_SKILL_CONVENTIONS__` defines that `src/kernel/static-skills.ts` reads; absent assets ⇒ empty defines ⇒ `STATIC_FILES` is empty, which is exactly what happens under `tsx` in tests.
- `npm test` — `pretest` builds `@vault-mcp/core`, then `tsc --noEmit && node --import tsx --test`. **The `pretest` is load-bearing, not tidiness:** the tests import published core contracts, which resolve to `packages/core/dist` — the COMPILED output. Without the rebuild you test the previous build's bytes.
- Install for testing: copy `main.js` + `manifest.json` into `<vault>/.obsidian/plugins/vault-skills/` and reload the plugin. During development add an empty `.hotreload` file in that directory so the hot-reload plugin picks up rebuilds — it belongs to the vault install, not to this repo.

## Headless testing

Everything except `obsidianSkillsBackend` is unit-tested without Obsidian: the compiler core runs over an injected `SkillsSource`, the tool handlers over a fake `SkillsBackend`, the accept guard over plain objects, the export-on-save debounce and change-relevance predicate over plain values, and the settings adoption over plain records. `obsidianSkillsBackend` (the `app.vault` / `app.metadataCache` / `app.fileManager` adapter), the pane, and the modals are the parts that need a running Obsidian. Keep new logic on the Obsidian-free side of that line — it is why this package moved between three homes without losing coverage.
