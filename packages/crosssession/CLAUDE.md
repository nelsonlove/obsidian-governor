# Vault Cross-session (plugin id `vault-crosssession`) — architecture & working notes for Claude Code

The fleet's coordination channels as their own Obsidian plugin: channel discovery by frontmatter, delta reads against a per-handle read position, read-receipt attestation, and posting that is refused while you are stale — published to the Governor host through `vault-mcp-api`. Extracted from the host at the suite split's S6 (`docs/suite-split-design.md` §6, "Cross-session | private operator | satellite"), following `packages/quickadd-choices-compile` (the pilot), `packages/skills` (S4) and `packages/triage` (S5). Package layout, build/test commands, and the extraction's four consequences are in `README.md`; the user-facing model is `docs/crosssession.md` at the repo root.

## Locked decisions (don't relitigate without reason)

- **The published tool names CHANGED, and that was a deliberate trade — this is the one thing to know before touching anything here.** `crosssession_channels` / `_delta` / `_attest` / `_post` are now `vault_crosssession_channels` / `_delta` / `_attest` / `_post`. The host publishes an external tool as `<sanitized publisher id>_<bare name>`, so **the plugin id and the tool namespace are the same string**; `vault-crosssession` sanitizes to `vault_crosssession`. The alternative existed and was NOT taken: a plugin id of literally `crosssession` would have sanitized to `crosssession` and reproduced the shipped names exactly, the way `vault-skills` did for `vault_skills_*`. It was declined for the same two reasons triage's was — the extraction was specified with the id `vault-crosssession`, which is the suite's naming convention (`vault-skills`, `vault-triage`, `vault-crosssession`), and a bare `crosssession` is a collision-prone id in a global Obsidian plugin namespace. The cost is real and should not be understated: the host's own locked decision says renaming shipped tool names breaks agent sessions for zero semantic gain, and these four were live on the operator's own coordination channel. **If that trade is ever revisited, it is a one-line change** — `manifest.json`'s `id`, plus the strings in `tests/host-shim.mjs` and the settings tab's status line. Nothing else in the package encodes the prefix (the specs carry BARE names; the prefix is the host's).

- **`channel` is NOT a path key, and renaming it into one would be wrong — this is the decision that distinguishes this extraction from triage's.** The host's `PATH_KEYS` are `path`, `from`, `to`, `target_path`, `template_path`, `subdir`, `file_path`, `output_folder`. Triage renamed `target` → `target_path` because `target` WAS the destination the call named and the host could then scope it. Here the analogous move is wrong three times over:
  1. **It would not scope the write.** `post` appends to the channel folder's single entry-bearing log file, DISCOVERED inside the handler. No call argument names it. Path-keying `channel` would hand the guard the folder NOTE while the file actually written stays unscoped — the illusion of a check.
  2. **A `channel` value may be a uid.** The argument accepts uid | folder-note path | folder. `isVisible` would normalize and prefix-match a bare uid as a path and refuse every uid-addressed call under an allowlist. That is precisely the bug the host fixed by renaming its scheme-write `to` → `to_address` **away** from a path key: an address string is not a path, and this is the same class.
  3. **It would expose the tool to the record-immutability guard on the wrong path** — see the next bullet.
  The consequence is that all four tools are blocked wholesale under an active allowlist. That is fail-closed, strictly stricter than the in-tool filter it replaces, and is stated in the README, the settings tab and `docs/crosssession.md`. Pinned by test (`publication: … NOT ONE argument is a host path key`), which also asserts `channel` is absent from a SNAPSHOT of the host's list (tests/host-shim.mjs) — a review aid, not a live tripwire; the test that actually fires when the host adds the key is the host's own guard.test.mjs pin over the live `collectPaths`.

- **The record-immutability question was ANSWERED, not assumed, and `RECORD_EXEMPT_OPS` was NOT widened.** The host's exemption set (`src/kernel/record-guard.ts`) named `crosssession_post` as the one other pure-EOF-append tool, deliberately unexempted because it was "unreachable by this check today". Both halves were re-verified at S6 and both still hold. **It was never outside the kernel:** as a module tool it registered on the same guard-patched `server.registerTool` every built-in rides, and as a published external tool it registers through the identical `external-tools.ts` → `makeGuarded` path — so "unreachable" never meant "bypasses the dequeue closure". **It is unreachable on arguments:** `collectPaths({handle, channel, body})` is empty because `channel` is not a `PATH_KEY`, and the appended file is discovered rather than named. The argument names did not change, so `vault_crosssession_post` reaches the check with the same empty list and is refused by it exactly as often as before: never. Adding it to the set would therefore change no behavior while widening a protective set on a guess — which is what the original bullet forbids. What DID change is the documentation: the host's comment, its CLAUDE.md bullet and its test now name the new tool identity and record the re-verification. (Incidental fact checked at the time, and not load-bearing either way: neither the live channel's folder note nor `CROSS-SESSION.md` carries `record: true` — the log note carries `auto-accept: appends`.)

- **`ctx.visible` / `ctx.getSettings` are dormant seams, kept deliberately.** Nothing supplies them in the shipped configuration, exactly like the triage satellite's and the skills satellite's `preview` filter. Do not delete them: their tests supply them (via a local `visiblePaths` over core's published `isVisible`) so they cannot rot, and a `vault-mcp-api` that can carry the caller's scope to a publisher (apiVersion 2) makes them live again with no code change.

- **THE ENTRY FORMAT AND THE APPEND PRIMITIVE MAY NOT DRIFT.** The fleet's `CROSS-SESSION.md` is live and is written by three parties: this plugin, a human in Obsidian, and shell `>>` heredoc appends. `post` writes `"\n## <stamp> · <handle>\n\n<trimmed body>\n"`, and `obsidianCrosssessionSource.append` inserts the file's own missing trailing newline first (so a hand-edited log never gets a heading glued onto its last line) and goes through `vault.process`, Obsidian's atomic read-modify-write. Changing either is changing a file format three writers share. Pinned byte-exactly by the happy-path test.

- **The receipt store moved, so its state had to move with it.** `crosssession-receipts.json` sat in the HOST's plugin dir beside the journal and `install-id.json`. It is live operational state, not config: losing it makes every affected handle's next `delta` re-serve entries it already read and its next `post` refuse `stale_read` on entries it already attested. `main.ts` therefore runs a SECOND one-shot adoption, by merge (own values win per channel + handle), under its own latch — separate from the config latch because the two sources are independently present (the operator's live host has receipts and no config override). Rule 1 is structural here rather than merely intended: `ReceiptStore.loadFrom` takes a directory and there is **no `saveTo` counterpart**, so nothing in this package can write the host's copy.

- **Config is read PER CALL, never captured.** `CrosssessionToolsCtx.config` is a thunk. But the tool DESCRIPTIONS are necessarily build-time snapshots of it — `channels`' description renders the configured channel fileClass, and the host snapshots a published spec's schema and description when it registers it — so `main.ts` **disposes and re-publishes on every settings write**, the triage satellite's pattern. As a module the specs were rebuilt per connection; this restores that freshness. Do not "simplify" `republish()` back into a single `this.register(publishTools(...))` in onload: a renamed channel fileClass would be misreported to every agent reading the tool list until an Obsidian reload.

- **Re-apply every schema bound in the handler.** The SDK converts zod to JSON Schema and the host converts it back through a small subset (`src/mcp/json-schema-to-zod.ts`): `type`, `description` and string `enum` survive; `default`, `min`, `max`, `pattern` do NOT. Every `.min(1)` therefore runs again in `requireText`. This is the `vault_skills_release` semver bug, avoided rather than repeated — if you add a constrained argument, constrain it twice.

- **Handlers return plain data and THROW on refusal**, with a lowercase-snake `code` on the error; the host's `fail()` renders `Error [code]: message`. There is no `ok`/`fail`/`codedError` import here — those helpers are host-internal. **Unlike the triage extraction, NO envelope changed:** this surface never used `okError`, so every typed refusal (`stale_read`, `channel_unresolved`, `invalid_handle`, `invalid_body`, `stamp_ahead`, `no_log_file`, `log_ambiguous`) is byte-compatible with the folded era. One envelope shape is load-bearing and easy to break: `post`'s success object carries `filesChanged` / `files`, which is the host's `reportedEffects` convention — it survives the boundary only because the host wraps a returned object as `ok(data)`, making it the `structuredContent` the kernel reads. Removing those two keys silently empties the journal record's `effects` field for the one tool whose write target is never in its arguments.

- **The staleness gate is COOPERATIVE, and saying otherwise is the failure mode to avoid.** `handle` is self-declared and unauthenticated. A session that lies about its handle defeats the check for itself, exactly as a session that lies in a log entry defeats the log. The threat model is honest lapses — posting without having read — not adversaries. Do not describe attestation as authority, permission, or identity; it grants nothing, gates only this plugin's own `post`, and writes no note.

- **`isVisible` comes from `@vault-mcp/core`, and nothing here re-implements it.** Same reasoning as S4: a second copy of a guard predicate is the drift this repo has paid for twice. The test's `visiblePaths` helper is defined over it rather than beside it.

## Build / test

- `npm run build` — esbuild, emits `main.js`. No assets, no defines: like the triage satellite and unlike skills, there is nothing to embed.
- `npm test` — `pretest` builds `@vault-mcp/core`, then `tsc --noEmit && node --import tsx --test`. **The `pretest` is load-bearing, not tidiness:** the tests reach `isVisible` through `packages/core/dist` — the COMPILED output. Without the rebuild you test the previous build's bytes.
- Install for testing: copy `main.js` + `manifest.json` into `<vault>/.obsidian/plugins/vault-crosssession/` and reload the plugin. During development add an empty `.hotreload` file in that directory so the hot-reload plugin picks up rebuilds — it belongs to the vault install, not to this repo.

## Headless testing

Everything except `src/obsidian-source.ts` and `src/settings-tab.ts` is unit-tested without Obsidian: the parser and ordering are pure over strings, the tool handlers run over a fake `CrosssessionSource`, the receipt store over a fake `ReceiptAdapter`, and both adoptions over plain records. `tests/host-shim.mjs` reproduces the three things the host does to a published tool — the `<sanitized id>_<bare name>` naming, the `ok()`/`fail()` envelopes including the coded rendering, and the annotations it derives from an UNTRUSTED `readOnly` claim — so the tests assert the envelopes an agent actually sees rather than raw return values. It also carries the host's `PATH_KEYS` **as data**, so this package can assert what its own argument names are NOT.

It deliberately does NOT reproduce the F3 pathless-tool block, the path allowlist, the write queue, the journal, read-only mode, or the record-immutability guard. Those are host code with host tests, and a second copy could drift into asserting a posture the host does not enforce. The module's suite used to test several of them by constructing a real `Kernel` + `makeGuarded`; that was possible only because it lived in the host's tree, and those assertions belong where the code is.

`src/obsidian-source.ts` is NOT reached headlessly — unlike the triage satellite, there is no link-healing property here that demands driving the real adapter, because this plugin never moves or renames anything. Its two un-headless surfaces are the duck-typed vault reads and the `vault.process` append; verify them live against a running Obsidian.
