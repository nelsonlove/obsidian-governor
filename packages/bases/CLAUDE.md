# Vault Bases (plugin id `vault-bases`) — architecture & working notes for Claude Code

Obsidian's own Bases engine as an agent surface, in its own Obsidian plugin: `.base` enumeration, and evaluated view rows harvested from a hidden background leaf — published to the Governor host through `vault-mcp-api`. Extracted from the host at the suite split's S7 (`docs/suite-split-design.md` §6/§7, "Bases | public optional | satellite"), the first of the optional tier, following `packages/quickadd-choices-compile` (the pilot), `packages/skills` (S4), `packages/triage` (S5) and `packages/crosssession` (S6). Package layout, build/test commands, and the extraction's four consequences are in `README.md`; the user-facing model is `docs/bases.md` at the repo root.

## Locked decisions (don't relitigate without reason)

- **THE SERIALIZER MOVED, AND THAT IS THE DECISION TO UNDERSTAND BEFORE TOUCHING ANYTHING HERE.** The S5 triage extraction deliberately left `queryBaseRows` and the hidden-leaf capture in the host, on the grounds that "a copy of the serializer in a second plugin would race the one in this plugin over the one leaf" — a claim repeated in `packages/triage/CLAUDE.md`, `packages/triage/README.md`, `docs/bases.md`, `docs/suite-split-design.md` and the host's `tools-bases.ts`. **That reasoning is correct and it does not block this extraction, because triage was a would-be second CONSUMER while bases is the OWNER of the leaf and of the serializer.** A move leaves one copy. A copy would have left two. The distinction is the whole argument, and it was verified rather than asserted:
  - `queryBaseRows`' only production call site anywhere in the repo was `base_query`'s own handler (`tools-bases.ts:332` before the move); every other reference lived in its own test file.
  - `captureSerializer` (`const captureSerializer = makeSerializer()`) had exactly one call site, inside `queryBaseRows`.
  - `makeSerializer` and `captureWithCleanup` were used only by the three source files that moved.
  - `packages/triage/src/tools.ts`'s `baseQuery?` ctx seam is a **shaped type nothing ever supplies** — it imports nothing from the host and its handler refuses `bases_unavailable`. Not a consumer.
  - After the four `git mv`s, `grep -rn "queryBaseRows\|makeSerializer\|captureSerializer\|captureWithCleanup" packages/plugin/src` returns **nothing**.

  The mirror-image risk is real and is exactly why this had to be a MOVE and never a copy: had the host kept its copy, the two serializers would race over the one leaf, which is the failure S5 refused. If anyone ever proposes re-adding a bases capture path to the host, that is the argument to raise.

- **The serializer must stay MODULE-SCOPED, not per-registration.** `const captureSerializer = makeSerializer()` sits at module scope in `tools.ts`. `main.ts` rebuilds the specs on every settings write and the host snapshots a spec set per connection, so a serializer constructed inside `buildBasesTools` would serialize nothing — two connections would fight over the one hidden leaf. The pin travelled with the tests: "serialization is MODULE-WIDE: captures from two separately-built spec sets still run one at a time" is the module-scope regression test (formerly worded against two `registerBasesTools` calls; the property is identical). Keep it.

- **The published tool names changed TWICE OVER, and that was a deliberate trade.** `base_list` / `base_query` are now `vault_bases_list` / `vault_bases_query`. Two compositions: the host publishes an external tool as `<sanitized publisher id>_<bare name>`, so **the plugin id IS the tool namespace** (`vault-bases` → `vault_bases`); and the BARE names shed their `base_` prefix, because keeping them would have published `vault_bases_base_list` / `vault_bases_base_query`.

  | shipped (module) | bare name here | published (satellite) |
  |---|---|---|
  | `base_list`  | `list`  | `vault_bases_list`  |
  | `base_query` | `query` | `vault_bases_query` |

  The cost is real and should not be understated: **it breaks any agent session or saved prompt calling the old names**, and the host's own locked decision says renaming shipped tool names breaks agent sessions for zero semantic gain. What buys it is that the stuttering alternative is worse to read and to type, and that one rename motion is cheaper than two. **Reversing it is a one-line change** — `manifest.json`'s `id`, plus the strings in `tests/host-shim.mjs` and the settings tab's status line. Nothing else encodes the prefix (the specs carry BARE names; the prefix is the host's). Pinned by the `publication` test.

- **The allowlist posture is ASYMMETRIC, and BOTH halves must be stated — one tightens, one loosens.** The host's F3 gate (`packages/plugin/src/mcp/external-tools.ts:209-229`) is evaluated **at call time on the ACTUAL ARGUMENTS**, not on the declared schema: `if (settings.allowlist.length > 0 && collectPaths(args ?? {}).length === 0) return fail(...)`.
  - **`vault_bases_list` takes NO arguments** ⇒ blocked outright under an active allowlist, where the module filtered its listing. Strictly stricter, fail-closed.
  - **`vault_bases_query` takes `path`**, which IS in the host's `PATH_KEYS` ⇒ NOT blocked. The host's guard SCOPES it and refuses `out_of_allowlist` for a hidden `.base`. The in-handler `pathVisible` belt is DORMANT (nothing supplies `ctx.visible` in the shipped configuration); the ENFORCED check is the host's.
  - **The ROW filter is dormant, and that is a real reduction in containment.** `boundRows`' allowlist drop and `some_rows_hidden` both need `ctx.visible`, which a satellite cannot get — and the host's guard checks the `path` ARGUMENT, never the row paths the engine discovers. So under an allowlist, a query on a VISIBLE base can return rows for notes OUTSIDE it — each row carrying the hidden note's path AND its evaluated property values (frontmatter fields and formula outputs rendered through the view's columns; frontmatter-derived content, never body text), where the module dropped the whole row. **Do not write "the host scopes it" and stop there** — the host scopes the base you name, not the notes the answer contains. It re-lights when `vault-mcp-api` can carry the caller's scope to a publisher (apiVersion 2, the item triage and cross-session both named). Filed for the host to decide on.
  - Both tools declare `readOnly: true`, which the host DISTRUSTS unless `vault-bases` appears in the user's **`trustedReadOnlyPlugins`** setting. Untrusted ⇒ both register as MUTATING, so read-only mode blocks both and each takes a write-queue slot and a journal record. Trust restores read-only-mode availability but does NOT change the F3 gate (closed 2026-09-05 by the skills satellite review: trust answers read-only mode, never scoping).
  - **This is not issue #381.** #381 names `obsidian_health`, `provenance_reconcile` and `obsidian_conformance_debt`. Bases is not one of them and this extraction does not resolve it. What may honestly be said is the asymmetry above.

- **`ctx.visible` / `ctx.getSettings` are dormant seams, kept deliberately.** Nothing supplies them in the shipped configuration, exactly like the skills, triage and cross-session satellites'. Do not delete them: their tests supply them (via a local `visiblePaths` over core's published `isVisible`) so they cannot rot, and apiVersion 2 makes them live again with no code change.

- **The feature gate survived the move, at a coarser GRAIN.** `source.available() === false` ⇒ `buildBasesTools` returns an EMPTY spec list and nothing is published — the fileclass precedent: an enabled plugin on a pre-1.10 Obsidian is ABSENT, not broken. What changed is when it is evaluated: per `republish()` (plugin load + every settings write) rather than per connection build. So an Obsidian upgrade, or re-enabling the Bases core plugin, does not surface the tools until the plugin is reloaded. Stated in the README and in the settings tab rather than left to be discovered.

- **`invalid_path`: a backslash in `path` is refused outright, before every other path check.** New refusal code at this extraction, and the same rule the triage satellite adopted at `packages/triage/src/kernel/plan.ts:75`. Every check downstream — this package's `.base` suffix test, `pathVisible`, and the host guard's own `isVisible` — splits on `/` alone, so `Views\..\..\secret.base` reads as ONE opaque segment here and as a traversal to whatever normalizes it later. Obsidian paths never legitimately contain a backslash; refusing is free and closes the class rather than the instance. Pinned by test on both the tool handler and the seam.

- **Re-apply every schema bound in the handler.** The SDK converts zod to JSON Schema and the host converts it back through a small subset (`packages/plugin/src/mcp/json-schema-to-zod.ts`): `type`, `description` and string `enum` survive; `default`, `min`, `max`, `pattern` do NOT. So `path`'s `.min(1)` and `limit`'s `.int().min(1)` run again in the handler (`requireText`, `optionalPositiveInt`). This is the `vault_skills_release` semver bug, avoided rather than repeated — if you add a constrained argument, constrain it twice.

- **Handlers return plain data and THROW on refusal**, with a lowercase-snake `code` on the error; the host's `fail()` renders `Error [code]: message`. There is no `ok`/`fail`/`codedError` import here — those helpers are host-internal. **No envelope changed:** this surface never used `okError`, so every typed refusal (`bases_unavailable`, `not_a_base`, `out_of_allowlist`, `not_found`, `base_parse_error`, `view_not_found`, `base_timeout`) is byte-compatible with the folded era; `invalid_path` and `invalid_argument` are additions, not replacements. `queryBaseRows` keeps its `{refusal} | {result}` RETURN shape rather than throwing — it is the seam, its tests drive it directly, and the tool handler is the one place that converts a refusal into a throw.

- **Config is read PER CALL, never captured.** `BasesToolsCtx.config` is a thunk. But the tool DESCRIPTIONS are necessarily build-time snapshots of it — `query`'s renders the row cap AND the query timeout, and the host snapshots a published spec's schema and description when it registers it — so `main.ts` **disposes and re-publishes on every settings write**, the triage/cross-session pattern. As a module the specs were rebuilt per connection; this restores that freshness. Do not "simplify" `republish()` back into a single `this.register(publishTools(...))` in onload: a raised timeout would be misreported to every agent reading the tool list until an Obsidian reload, and the feature gate would stop being re-evaluated too. Pinned by the "descriptions render config values" test.

- **One adoption, not two, and the absence was checked.** Config adopts once from the host's `modules.bases.config` under the three rules (never write the host's settings; run once; own values win). Cross-session needed a SECOND, separately-latched adoption because it had live operational state outside `data.json`. **This surface has none** — read-only end to end, no state file, no cache, no note it ever wrote; the capture leaf is constructed and detached inside a single call. Recorded so the absence is a finding rather than an oversight, and pinned by a test over `DEFAULT_PLUGIN_SETTINGS`' key set.

- **`hostSettings === undefined` means HOST NOT READY, never "host with empty settings".** The host declares `settings` without an initializer and assigns it mid-`onload`, so an instance visible in `app.plugins.plugins` before that assignment must not burn the one-shot latch. The check in `main.ts` is `host.settings !== undefined`, not a truthiness test. Found by the skills extraction's review; do not "tidy" it into `if (host?.settings)`.

- **No stale `modules.bases.config.*` or `base_query` pointers in shipped strings.** The settings-tab help text is ported verbatim from the host's `BASES_CONFIG_FIELDS` minus the dead `modules.bases.config.` prefixes, with `base_query` respelled `vault_bases_query` — both of the old spellings name nothing in this plugin, and a string pointing at a path that does not exist is worse than no string. Pinned by test over the field help AND the tool descriptions.

- **`isVisible` comes from `@vault-mcp/core`, and nothing here re-implements it.** Same reasoning as S4: a second copy of a guard predicate is the drift this repo has paid for twice. The test's `visiblePaths` helper is defined over it rather than beside it.

- **`tests/host-shim.mjs`'s `HOST_PATH_KEYS` is a REVIEW AID, never a live tripwire.** It is a snapshot copy of the host's `PATH_KEYS` + `ARRAY_PATH_KEYS`, carried as DATA so this package can assert which of its own argument names are on the list (`path`) and which are not (`view`, `limit`). It does not read the host's source and it will NOT fail when the host changes its list — it only makes such a change show up as a diff a reviewer must reconcile. The pin that actually fires lives in the host's own `tests/guard.test.mjs`, over the live `collectPaths`. Do not claim otherwise in a comment or a report.

## Build / test

- `npm run build` — esbuild, emits `main.js`. No assets, no defines: like the triage and cross-session satellites and unlike skills, there is nothing to embed.
- `npm test` — `pretest` builds `@vault-mcp/core`, then `tsc --noEmit && node --import tsx --test`. **The `pretest` is load-bearing, not tidiness:** the tests reach `isVisible` through `packages/core/dist` — the COMPILED output. Without the rebuild you test the previous build's bytes. Note the suite takes ~6s: the belt-deadline test really waits out a 1s timeout plus the 5s grace, deliberately, because a faked clock there would not prove the chain moves on.
- Install for testing: copy `main.js` + `manifest.json` into `<vault>/.obsidian/plugins/vault-bases/` and reload the plugin. During development add an empty `.hotreload` file in that directory so the hot-reload plugin picks up rebuilds — it belongs to the vault install, not to this repo.

## Headless testing

Everything except `src/obsidian-source.ts` and `src/settings-tab.ts` is unit-tested without Obsidian: the `.base` interpretation and propertyId normalization are pure over parsed YAML, the capture lifecycle and serializer are pure over promises and an injectable timer, the tool handlers run over a fake `BasesSource`, and the adoption runs over plain records. `tests/host-shim.mjs` reproduces the three things the host does to a published tool — the `<sanitized id>_<bare name>` naming, the `ok()`/`fail()` envelopes including the coded rendering, and the annotations it derives from an UNTRUSTED `readOnly` claim — so the tests assert the envelopes an agent actually sees rather than raw return values.

It deliberately does NOT reproduce the F3 pathless-tool block, the path allowlist, the write queue, the journal or read-only mode. Those are host code with host tests, and a second copy could drift into asserting a posture the host does not enforce. The module's suite used to test several of them by mounting through `modules-mount.ts` against a `fakeServer`; that was possible only because it lived in the host's tree, and those assertions belong where the code is. What replaced them is the `publication` block: the wire names, the untrusted read-only claim, the path-key asymmetry, the re-applied schema bounds and the coded rendering.

`src/obsidian-source.ts` is NOT reached headlessly. Its three un-headless surfaces are the detached-`WorkspaceLeaf` construction, the hidden-host `isShown` trick, and the polled read of the engine's own `BasesView.data`; every hop is duck-typed and feature-checked, and a missing shape degrades to a `base_timeout` refusal rather than a crash or a hang. Verify it live against a running Obsidian — the original live smoke (Obsidian 1.13, 601 rows for a view whose filter matches exactly 601 notes) is recorded on issue #243's PR.
