# Governor (plugin id `governor`) — architecture & working notes for Claude Code

An Obsidian plugin (id `governor`; `vault-mcp` before 0.12.0) embedding an MCP server with direct `app.*` access, reached by Claude Code via a Unix socket + bundled stdio bridge. Local-with-Obsidian counterpart to the remote, filesystem-only `obsidian-vault-mcp-server` (JD 92046). Design specs and implementation plans live in the vault at `00-09 System/07 Repositories/07.36 obsidian-governor/` (renamed with the repo on 2026-08-19; the `06.20 obsidian-vault-mcp-plugin` slot it replaced, and the older JD 92050 one, are both retired).

## Locked decisions (don't relitigate without reason)

- **Naming (0.12.0, Nelson's ruling — one brand).** The product/project/framework is **Governor**. The plugin id is `governor` (migrated from `vault-mcp` in 0.12.0; the old id is historical). The acceptance capability's module id is `acceptance` (migrated from `governance`; a legacy `modules.governance` settings row is adopted once by `migrateLegacyModuleIds`). **Deliberately historical, do NOT rename:** the shipped always-on tool names `governance_revisions` / `governance_submit_revision` (renaming shipped tool names breaks agent sessions for zero semantic gain), the `@vault-mcp/core` workspace package name, and the on-disk state dir `<plugin dir>/governance/` (its files are live operator state; moving them is an S3 migration item, not a rename). (**The source dirs came OFF this list in S1** — the suite split, adopted by Nelson 2026-08-25, needs the host/governor boundary to be structural, so `src/kernel/governance/` → `src/governor/kernel/` and `src/governance/` → `src/governor/wiring/`. The old entry's reasoning — "churns every import for zero user-visible gain" — held while the two halves shipped as one plugin; §2 of `docs/suite-split-design.md` makes them two, and the churn is the point.) (The local directory name WAS on this list; Nelson reversed that on 2026-08-19 and renamed it to `obsidian-governor` to match the remote — a repo slot is named after the repository. `~/repos/system/obsidian-governor` is the path; the old `~/repos/obsidian-vault-mcp-plugin` survives only as a convenience symlink.) Env vars are `GOVERNOR_*` with the `ASSENT_*` spelling accepted as a fallback alias (GOVERNOR_ wins when both are set).

- **Source layout: two subtrees, one artifact (S1 of the suite split).** `src/governor/` holds everything the governance provider will ship as its own plugin — `src/governor/kernel/` is the pure logic (proposals, verification, admission, cohorts, mandates, transformations, history contracts, the accept/gesture kernel) and `src/governor/wiring/` is its Obsidian-facing layer (review pane, event wiring, git history store, observation store, territories, the proposal-producing write observer). **Everything else under `src/` is host.** One `main.js` still builds from both — S1 moved directories and imports, nothing else. The boundary is enforced, not merely described: `tests/host-governor-boundary.test.mjs` enumerates every host→governor import and every governor→host import (the dependency S3 must publish or copy), and fails on an unlisted one. Adding a crossing is legitimate — adding it *silently* is not. Do not reintroduce `src/governance/` or `src/kernel/governance/`.

- **THE GOVERNANCE SEAM (`src/mcp/seam.ts`, S2 of the suite split).** The host's hook API for an optional governance provider, built and consumed IN-TREE — still one plugin artifact, so the seam's sufficiency is proven at zero distribution risk. It ships on the same `plugin.api` object `external-tools.ts` defines (`apiVersion` stays **1**: the seam's methods are additive, and a bump would make every published `vault-mcp-api` build refuse to register).
  - **Two hook classes, and there will never be a third.** `registerWriteObserver(id, observe)` — post-write, observe-only, the host ignores the return value. `registerSessionRefusal(id, refuse)` — consulted at dequeue, returns `{code, detail} | null`. **Refusal-shaped, never boolean:** `null` is *silence*, not an allow, so the type cannot express permission and a registrant cannot un-refuse what the host or another registrant refused. Anything that could mutate a write in flight or assert acceptance is the class the seam must never offer.
  - **No `registerWriteVeto`.** §5 sketched one; S2 looked for a real registrant and found none (the fuller accept-transition guard is host-side in `@vault-mcp/core`, and the legacy-writer guard is a provider-internal `BaselineStore` predicate off the MCP write path). Unused perimeter surface is dead code. It lands when something needs it, with its round-trip test.
  - **Disposer-only revocation.** Every `register*` returns a disposer and the disposer is the ONLY address; `id` is a diagnostic label and an owner name, never an address. Same fix applied to `ExternalToolRegistry`: **`unregisterTools(ownerPluginId)` is GONE** from the host and from the `vault-mcp-api` SDK — it let any caller holding the api object revoke any publisher's tools. The SDK always used the disposer, so publishers are unaffected.
  - **Hook lists are module-private**, in a WeakMap keyed by a token only `createGovernanceSeam`'s two returned objects hold (the `governor/wiring/wiring.ts` pattern). `main.ts`'s external-tool registry and seam moved into module-level WeakMaps for the same reason — a `private` class field is compile-time privacy only, so `app.plugins.plugins.governor.externalRegistry` was walkable. Registration stays reachable and that is fine; the LIST of what everyone else registered must not be.
  - **Budgets.** The session refusal runs inside the kernel's queued closure (where `sessionLive` ran), so `WRITE_TIMEOUT_MS` bounds it. Observers are dispatched OFF the caller's result path — one `queueMicrotask` per hook, every failure caught — so a hanging or throwing observer cannot cost a caller a write that already landed. `WriteFacts` deep-freezes `operation` and `actor`; bytes are deliberately NOT copied per hook (§0's threat model excludes the actor a copy would defend against).
  - **What S2 moved.** The `propose` block left `mcp/server.ts` for `src/governor/wiring/write-observer.ts` behind the observer hook; the host keeps only the write-facts slot and `reportCompletedWrite`'s attribution guard. Session liveness is now the host's own expiry floor (`expiryRefusal`, `src/kernel/sessions/session.ts`) composed with the seam's refusal — **the session contract is HOST-owned** (the host mints; a session is transport state) while the session STORE and its revocation state stay with the provider. `ServerCtx` therefore names **zero** provider types, which is S2's exit criterion; provider tools arrive as `BuildOpts.providerTools` registrars from the composition root instead of as ports on the host's context. `mountAction` moved to `src/mount-state.ts` (the host drives the scheme panes with it too).
  - **Condition 6:** `obsidian_plugin_toggle` and `obsidian_plugin_uninstall` refuse a **registered governance provider's id**, the same way they already refuse the host's own — an agent doing cleanup must not be one call away from switching off the thing that reviews it. Simple refusal, not the persisted latch (that is on `reference/hostile-threat-model`).

- **Transport: Unix socket + bundled bridge.** Not HTTP. The `chmod 600` socket is the *only* auth boundary — no token, no listening TCP port (a localhost port is reachable by any local process and by browser DNS-rebinding; the socket isn't). `bridge.mjs` is built by esbuild and **embedded into `main.js`** via `define` (`__BRIDGE_SOURCE__` → `src/bridge-asset.ts`), then written to `~/.claude/governor/` on load (plus a grace-period copy at the legacy `~/.claude/vault-mcp/`). Never ship the bridge as a separate npm install. The bridge survives Obsidian restarts/plugin reloads: it captures the client's `initialize` handshake and, when the socket drops, fails in-flight requests, queues new ones, waits for the socket to return (`VAULT_MCP_RECONNECT_MS`, default 5 min), then replays the handshake to the fresh per-connection server and swallows the duplicate response.
- **Multi-client transport.** `UnixSocketListener` accepts each connection and `main.ts` builds a **fresh `McpServer` per connection** (`buildMcpServer`). So concurrent Claude Code sessions / background agents don't evict each other, and *conditional registration at build time is the dynamic-registration mechanism* — there is no `app.plugins.on("change")` + `tools/list_changed` machinery (obviated; new tools appear on session reconnect).
- **Per-connection options ride a preamble line** (`src/preamble.ts`, shared like ndjson.ts). The bridge may send `{"vault_mcp_preamble":1,…}` as the connection's FIRST line (on every attach, including reconnects — each connection is a fresh server); the listener peeks the first line and consumes it, passing anything else through untouched (old bridges stay wire-compatible — no preamble means default options). The reverse direction is gated too: the bridge sends the preamble only when the vault's discovery advertises `capabilities: ["preamble"]` — a newer bridge meeting an older plugin (the shared `bridge.mjs` is rewritten by whichever vault loaded last) warns on stderr and falls back to the full surface instead of feeding the old listener a bogus first message. Currently carries `code_mode`: capture all guarded registrations into a registry and expose only `obsidian_search_tools` / `obsidian_describe_tool` / `obsidian_call_tool` (`tools-code-mode.ts`). The meta-tools register UNguarded — the captured handlers carry the guard, so enforcement lands on the target call (guarding `obsidian_call_tool` itself would make read-only mode block reads).
- **State namespace: `~/.claude/governor/`** holds `bridge.mjs`, `<vault-slug>.sock`, `<vault-slug>.json`. Resolve `~` via `os.homedir()`. During the 0.12.0 grace period the legacy `~/.claude/vault-mcp/` dir also gets the bridge plus a `legacy: true` discovery copy pointing at the NEW socket (old registrations keep working); the bridge and the connect plugin's health probe read both dirs, skipping `legacy` duplicates.
- **Never write `~/.claude.json` directly.** Registration goes only through spawning the `claude` binary (`claudeRegister` in `src/claude-cli.ts`). When spawning `claude`, augment PATH (`spawnEnv`) — Obsidian's GUI PATH is minimal and the `claude` launcher shim runs `#!/usr/bin/env node`.
- **Plugin-gated tools gate on the LOADED instance** (`app.plugins.plugins[id]`), not `app.plugins.enabledPlugins` — `enabledPlugins` can list a configured-but-uninstalled plugin (stale entry).
- **`ok()` returns both `content` (text) and `structuredContent`.** `fail()` returns `isError: true`. `okError()` is ok()'s shape plus `isError: true` — for batch tools whose structured per-item report must survive a total failure (fail() would flatten it to text). Match the 92046 shapes; tool names are the identical `obsidian_*` set (strict-superset).
- **Safety guard** (`src/guard.ts`) is applied by monkey-patching `server.registerTool` in `buildMcpServer` (single interception point). A tool is mutating iff `annotations.readOnlyHint === false`. Read-only mode blocks mutating tools; the path allowlist normalizes paths (`posix.normalize`, reject `..` escapes) before prefix-matching. The wrapper itself lives in `src/mcp/guarded.ts` (`makeGuarded`) — separate from `server.ts` so it pulls in nothing from `obsidian` and is unit-testable.
- **Kernel v0** (`src/kernel/`) — the Assent kernel's first capabilities, shipped as transport hardening. They all bind at the SAME interception point as the guard, keyed on the same `readOnlyHint === false` discriminant, so "guarded", "serialized", "journaled", "conditional" and "idempotent" are one set by construction.
  - **Serialized write queue** (`write-queue.ts`) — every mutating call runs through one FIFO queue; reads never queue. The queue is a **plugin singleton** created in `main.ts` and carried into each per-connection server via `ServerCtx.kernel` — per-connection would serialize nothing, since concurrent sessions are the whole point. Each operation gets `WRITE_TIMEOUT_MS` (30s, constant, not a setting); on expiry that operation is **abandoned** (Obsidian exposes no cancellation) and fails with a typed `WriteTimeoutError` rendered as `Error [write_timeout]: …`, and the queue runs the next one. The bridge must never wedge behind one stuck call. Non-reentrant: in Code Mode `obsidian_call_tool` registers unguarded, so only its target takes a slot.
  - **Write journal** (`journal.ts`) — one JSONL record per mutating operation in `.obsidian/plugins/governor/journal/YYYY-MM.jsonl` (UTC month, so filenames agree with record `ts`). Operation-centric: `{ts, op, target{path,uid,paths,ref}, actor{transport,client,connection,server?{vault,install,version}}, argsDigest, outcome, error?, durationMs, queueWaitMs, revBefore?, revAfter?, corrects?, ifRev?, idempotencyKey?, intent?, addressedAs?, dedupeOf?, lockNotice?, effects?}` (`outcome`: `ok|error|late-ok|late-error|conflict|deduped`). `addressedAs` (issue #91) is audit-of-intent beside `target`'s audit-of-effect: when a mutating call addressed by `uid:<v>`/`jd:<addr>`, the record carries `[{ref, path}]` — the form the caller used and what it resolved to at the interception point (enqueue-time call metadata like `argsDigest`, capped like `target.paths`, kept on deduped terminals like `intent`, absent for plain-path calls). **Append-only** — `append` is the only write path and no edit/delete/prune API exists. `target`, `revBefore` and the clock all sample **at dequeue**, inside the queued closure (an enqueue-time probe describes the operation ahead of you); `durationMs` is handler time, `queueWaitMs` is enqueue→dequeue. `target.ref` (`command:<id>`, `plugin:<id>`, …) is derived from well-known argument keys in `mcp/guarded.ts` (`REF_KEYS`, ordered most-identifying-first so an `id` outranks a `name`) — a fallback for pathless mutators, never overriding a real path; deliberately un-namespaced, since `op` already disambiguates two tools sharing an argument name. Because records are never rewritten, an abandoned operation that settles after its timeout appends a **corrective record** (`outcome: late-ok|late-error`, `corrects: <original ts>`, fresh `revAfter`) via the queue's `onLate` hook. Note bodies never land: `digestArgs` summarizes body keys and long strings as `<N chars>`. Journal failures `console.error` and are swallowed — a broken journal must never fail a vault operation. `uid` (frontmatter) and `rev` (mtime) come from `TargetProbe` (`obsidian-probe.ts`, the only kernel file that imports `obsidian`). A **throwing probe** never masks a result: at dequeue it fails the call as `ProbeError` (message prefixed `probe:` so the journal doesn't blame the vault operation), and on the record-only paths (`revAfter` in `finally` and in `onLate`, `uid` on terminal records) it is swallowed and the field is simply absent.
  - **`intent`** (B2) — the third kernel argument: advisory agent-authored "why" text on any mutating call, declared/peeled exactly like `if_rev` (handlers never see it, so it structurally cannot reach note frontmatter). **Journal-only**: recorded verbatim on the record beside op/actor (`JournalRecord.intent`) for review surfaces to display as "agent says" — never trusted, never interpreted, NEVER an acceptance signal (nothing in the kernel reads it back). Deliberately NOT part of idempotency identity (unlike `if_rev`): advisory text doesn't change what was written, so a replay may reword it and every record — including `deduped` terminals, unlike `ifRev` — keeps its own call's text. Degrades quietly without a kernel (peeled and dropped; nothing destructive about losing a description). Max 2000 chars.
  - **`if_rev` + `idempotency_key`** — kernel arguments, not tool arguments. `withKernelArgs` (`mcp/guarded.ts`) adds both to the `inputSchema` of every MUTATING registration at the interception point — mandatory, not decoration: the SDK parses args with `z.object`, which STRIPS undeclared keys, so an undeclared `if_rev` would never reach the wrapper. `makeGuarded` peels both off the args (handlers never see them) and passes them to `Kernel.runMutation` as `MutationContext.ifRev` / `.idempotencyKey`. `if_rev` is compared to the live rev **at dequeue**, in the same closure that samples `revBefore` — an enqueue-time check compares against the world the operations ahead of you already changed, which is the lost update the feature exists to catch. Mismatch ⇒ `RevConflictError` ⇒ `Error [rev_conflict]: …`, no write, journal `outcome: "conflict"`. Unreadable rev (missing file, no probe) fails closed. Multi-target ops check the FIRST target — for a move that is the SOURCE (`from` is declared before `to`, and `collectPaths` walks in declaration order; pinned by a test). **With no kernel** (`opts.kernel` absent — tests, bare embeds) a mutating call carrying `if_rev` is REFUSED (`Error [precondition_unsupported]`) rather than written unconditionally: an unenforceable precondition must not fail open. `idempotency_key` degrades quietly there instead, because its failure mode is at-least-once rather than destructive. Idempotency (`kernel/idempotency.ts`) is settled BEFORE the queue, and the key is **reserved at entry** (`IdempotencyStore.claim` — a synchronous check-and-set, no await in between, so concurrent retries cannot all become owner): one caller runs, the rest await its settlement and return the SAME envelope (journal `outcome: "deduped"`, `dedupeOf` = winner's `ts`) without a queue slot. **Waiters share the winner's outcome whatever it is** — a thrown failure is rethrown to all of them; only AFTER settlement does a thrown failure leave the key free for FUTURE calls. Key identity is (key, op, **args**, **kernel args**): a divergent op, divergent args, or a divergent — including newly present/absent — `if_rev` is `IdempotencyMismatchError` (`reason: "op" | "args" | "if_rev"`), never a silent replay that would discard a write while reporting success. `if_rev` is checked at claim time rather than folded into the args fingerprint, so the failure can name which half diverged and both revisions; the precondition is half of what the caller asked for, and replaying across it would assert a check that never ran. The args fingerprint (`fingerprintArgs`) is the stable-serialized `argsDigest` PLUS a hash of the full args — the digest collapses bodies to `<N chars>`, so equal-length bodies would otherwise collide. TTL 10 min, LRU cap 500, in memory per plugin instance (a reload clears it — the documented v0 boundary). Only RETURNED envelopes are stored (ok and isError alike); thrown failures (timeout, conflict) are not, so their keys stay retryable. `deduped` records OMIT `ifRev` (a replay never reaches the dequeue check, so recording it would assert a check that never happened) — as do the terminal mismatch records, for the same reason. Reads expose the matching `rev` via `RegisterFsToolsOpts.rev` in core (`obsidian_read_note` / `obsidian_read_notes`), sampled BEFORE the content so a racing write can only make it too old, never too new.
  - **Record immutability** (`record-guard.ts`, #264) — a mutating operation naming a note whose frontmatter carries `record: true` is refused at dequeue (`Error [record_immutable]`, same closure as the `if_rev` check, journaled `outcome: "error"` like any thrown kernel failure) UNLESS the op is `obsidian_append_note` — exemption by TOOL identity (`RECORD_EXEMPT_OPS`), never argument-sniffed; `obsidian_append_at_heading` CAN insert mid-file and is NOT exempt (its heading-absent + create_if_missing branch appends at EOF, but the common branch does not — an exemption keyed on a sometimes-append is the guess the set avoids) (`vault_crosssession_post` — the one other pure-EOF-append tool, since S6 a `vault-crosssession` satellite tool, spelled `crosssession_post` while it was a module here — is deliberately NOT exempted either. **Re-verified at the S6 extraction, and the answer did not change:** "unreachable" was never a claim that it escaped the kernel — as a module tool it registered on the same guard-patched `server.registerTool` as every built-in, and as a published external tool it registers through the identical `external-tools.ts` → `makeGuarded` path, kernel checks included. It is unreachable on ARGUMENTS: its target arrives as `channel`, which is not in `PATH_KEYS`, so `collectPaths({handle, channel, body})` is EMPTY and this check has nothing to test; the file it appends to is discovered inside the handler and named by no argument at all. `channel` was deliberately not renamed into a path key at the extraction — doing so would scope the folder NOTE rather than the appended file (the illusion of a check), would prefix-match a uid value as a path and refuse every uid-addressed call under an allowlist (the bug the `to` → `to_address` rename fixed, in reverse), and would expose the tool to THIS guard on the wrong path. So the set was NOT widened: listing it would still change no behavior while widening a protective set on a guess. The satellite pins its half — that none of its four tools carries a host path key — in `packages/crosssession/tests/`, so the day `channel` becomes path-keyed a test fails on both sides instead of a live coordination log silently starting to refuse). EVERY named path counts (a move ONTO a record overwrites it), via the same uncapped `collectPaths` list the lock consult uses. **Fails OPEN**, the deliberate mirror of `if_rev`'s fail-closed: the flag comes from `TargetProbe.record` (optional method; obsidian-probe.ts reads the metadata cache only — never disk), and a missing file / unparsed cache / throwing record probe / probe without the method refuses nothing — the check is protective, not load-bearing, and its try/catch lives inside `recordImmutableRefusal` so a throwing record probe is never promoted to the dequeue closure's fatal `ProbeError`. What counts as "true" is `isRecordFlag` (boolean `true`, or the quoted string `"true"`). Scope is ADDRESSED mutation — the paths an op NAMES: discovered-blast-radius ops (`obsidian_repoint_link`, a move's backlink-healing rewrite) can still touch a record's body as a side effect, a documented boundary (kernel-v0.md/reference.md), not a regression to "fix" by re-checking discovered paths without a design pass. **Toggle**: `enforceRecordImmutability` (default true) gates it at the PROBE (`obsidianProbe`'s `record()` returns `undefined` when off), so a disabled guard reuses the already-tested fail-open path instead of adding a second refusal branch to the kernel; read live per call. Pure core unit-tested in `tests/record-immutable.test.mjs`; Code Mode covered by construction (captured handlers carry the guard/kernel wrapper); the FS-failover server documents record immutability among its deliberate divergences (`fs-write-kernel.ts`).
  - **Advisory locks** (`locks.ts`, `mcp/tools-locks.ts`) — the claims mechanism, ADVISORY ONLY per ch4/ch8: it blocks nothing on account of another holder, and there is no accept/approve verb anywhere (claim / renew / release / list, never "grant"). `LockStore` is a plugin singleton on `Kernel.locks`; scopes are normalized path prefixes (segment-boundary matching, `""` = whole vault), TTL default 5 min / max 30 min, expiry is **lazy** (pruned by the next call — no timers) with an injectable clock. Overlapping claims by DIFFERENT holders are allowed and the claim response *discloses* them; a holder is `client#connection` (`holderOf`, derived from the journal actor — per connection, so a reconnect starts empty). On every mutating operation the kernel consults `locks.coveringAny(paths, holder)` **at dequeue** (same reason as `revBefore`) over **every path the arguments name, not just the primary** — a move INTO a claimed scope is as much somebody's business as a move out of one, and each lock is disclosed at most once however many paths it covers. Foreign claims add ONE `content` text block (claims joined by `\n`, closest first — a per-claim block would make the block count vary with vault state) + `structuredContent.advisory_locks` to the result and a `lockNotice` (most specific claim) to the journal record; the operation always proceeds. The holder's own writes into its own scope get nothing. The four tools register at the normal interception point; `claim`/`renew`/`release` are **`readOnlyHint: false` deliberately** — they mutate kernel state, not vault state, but journaling a claim matters more than the microseconds of queue slot, and `readOnlyHint === false` is the single discriminant that buys journaling. Consequences: read-only mode blocks claiming (nothing to disclose in a session that can't write), and claims carry the generic kernel args. `REF_KEYS` gained `lock_id`/`scope` so a claim journals `target.ref: "scope:<prefix>"` and a release/renew `"lock:<id>"`. Four adversarial-review fixes are load-bearing here and must not regress: **(D1)** the caps (`LOCK_MAX` 200 store-wide, `LOCK_MAX_PER_HOLDER` 50) **refuse** and never evict — the old eviction-of-globally-oldest let one client claiming in a loop silently destroy every other holder's live claims. `LockCapError` carries a code PER CAP (`Error [lock_cap]` for your own, `Error [lock_store_cap]` for the store's — one you clear by releasing, one you can only wait out) and the claim handler renders it with `codedError`, not core `fail()`, which would flatten it to a codeless `Error: …`. **Be precise about what the per-holder cap buys**: a holder is `client#connection`, so it bounds a CONNECTION — connections are free and the client name is self-asserted, so one client on four connections reaches 4 × 50 = 200 and a bystander is refused ("one flooding holder cannot fill the store" is FALSE and must not be re-asserted). Identity cannot fix that; TTL does. The real property is: per-connection 50, global 200, every claim expires within 30 min (5 default) with lazy pruning, so the store self-heals, and because claims are advisory-only a full store costs a denied caller the disclosure and nothing else — no vault data, no read, no write. The store-cap refusal message says so, so a denied bystander knows the wait is bounded; **(D2)** a same-holder same-scope re-claim REPLACES in place (same id, same `claimedAt`, new reason/expiry, `replaced: true`) instead of accumulating, and `obsidian_renew_scope` {lock_id, ttl_ms?} puts `store.renew` on the wire; **(D3)** the multi-path consult above; **(D8)** a claim's scope is checked against the **path allowlist** (`scopeRefusal` in tools-locks.ts, via `LockToolsCtx.getSettings`), with the whole-vault scope `""` refused explicitly because `collectPaths` drops empty strings — a session sandboxed to `Projects/` must not be able to stamp its name on every other session's writes. No allowlist ⇒ unrestricted, exactly as before. `obsidian_list_scope_claims` follows the same rule on the read side (#85): a claim is listed iff its scope path is itself inside the allowlist (the whole-vault scope `""` and prefix scopes broader than the allowlist are hidden — "within", never "overlaps"); hidden claims are COUNTED in `hidden_claims`, never named, so the disclosure ("territory outside your view is claimed") survives without the path oracle. No allowlist ⇒ byte-identical listing, no `hidden_claims` key.
  - **The uid index** (`uid-index.ts`, `mcp/tools-uid.ts`) — the identity substrate's first store (Delivery step 2), a plugin singleton on `Kernel.uids`. `uid → paths` plus the inverse `path → uid`, built at load from Obsidian's metadata cache and **never by reading files**. Obsidian-free like every other kernel module: it is defined over an injected `UidSource` (`paths()`, `uidOf(path)`); the adapter is `obsidianUidSource` in `obsidian-probe.ts` and the events are wired in `main.ts` (`wireUidIndex`) — `workspace.onLayoutReady` → `rebuild()` (before that the cache is still warming), then `metadataCache.on("changed")` → `onChanged` (covers uid added / changed / removed, and note creation), `vault.on("rename")` → `onRenamed`, `vault.on("delete")` → `onDeleted`, all via `registerEvent`. `onLayoutReady` takes a plain callback and returns no EventRef, so it is gated on a **disposed flag flipped by `this.register`** instead — an unload before layout must not rebuild an index for an instance that is gone. The whole wiring is **gated on `settings.enabled`**: with the socket down nothing can address a uid, so maintaining the index off every metadata event is work for no reader. **Duplicates are kept, never fixed**: a uid maps to ALL its paths in precedence order — `rebuild` sorts AND incremental `add` inserts in sorted position, so precedence is a property of the vault rather than of cache-warming or edit order (`onRenamed`'s in-place replacement is the one documented exception, and it is deliberate: a rename must not demote the note the uid currently resolves to) — `duplicates()` makes them queryable, and `requireOne` — the only resolution addressing may use — throws `UidAmbiguousError` rather than picking. Files with no uid are absent from the index entirely. `onRenamed` replaces the mapping IN PLACE (preserving a duplicate's precedence) and prefers what the index already knew to `source.uidOf(to)`, because at rename time the cache may not have re-keyed yet. The kernel takes `target.uid` from the index first and falls back to the `TargetProbe` frontmatter probe, so a uid lands on the record even when the cache is behind. `obsidian_resolve_uid` (read-only) is the lookup in both directions plus a no-argument duplicates report; it is **allowlist-filtered**, since an unfiltered index would be a path oracle for the area a sandboxed session is excluded from. The filter itself is `visiblePaths` in `guard.ts` (hoisted out of tools-uid.ts) because **uid ADDRESSING decides over the same set** — see below.
  - **uid addressing** (`uid:<value>`) — any path-bearing argument accepts `uid:<value>` and is rewritten to the real path in `makeGuarded`, BEFORE `guardCall`, for **reads and writes alike** (the guard wraps every registration, so one spot covers both — there is no separate read path). Per-tool support was never on the table: like the kernel args, the next path-taking tool would forget. It is defined over `mapPaths` in `guard.ts` — the walker `collectPaths` is now itself defined over — so the addressable set and the allowlist-scoped set are one set by construction. `mapPaths` returns the SAME object when nothing changed, so a call using no uid addressing behaves identically byte-for-byte. Resolution runs before the guard so the allowlist checks the RESOLVED path (a uid must not be a sandbox bypass); the resulting disclosure risk is closed by `uidSafe`, which folds resolved paths back to their `uid:` form in the refusal text. Unresolvable ⇒ `Error [uid_unresolved]`, ambiguous ⇒ `Error [uid_ambiguous]` naming the candidates; both refuse before the handler, before the queue, and are not journaled (nothing ran). **The candidate set is the allowlist-VISIBLE one** (`requireOne(uid, settings)` over `visiblePaths`, the same helper `obsidian_resolve_uid` uses): 0 visible ⇒ unresolved even when hidden carriers exist, 1 visible ⇒ resolve to it, 2+ visible ⇒ ambiguous naming only those. This is load-bearing and must not regress — `uid_ambiguous` used to name EVERY carrier, so a session sandboxed to `Projects/` learned an `Archive/…` path just by addressing a duplicated uid, which is the exact oracle `visible()` exists to close (`uidSafe` could not help: the leak was in the uid error, not the guard's). It also keeps the lookup and the addressing from disagreeing about what a uid names — they did before, the lookup resolving a duplicate the addressing refused. A consequence: a uid carried only outside the allowlist now refuses as `uid_unresolved` rather than `out_of_allowlist`, which is also less disclosure (it does not confirm the uid exists). No index ⇒ fail closed, never "treat it as a filename". `obsidian_resolve_uid`'s no-argument TOTALS are visible-filtered too (`UidIndex.indexedPaths()` → `visiblePaths`, then a Set for the uid count) — raw `size`/`uidCount` told a sandboxed session how much lives outside its allowlist, a cardinality oracle beside the path oracle. `visiblePaths` returns the SAME array when no allowlist is active, so the unfiltered case still reads the index's own counters.
  - **Scope-provider module** (`kernel/scheme/`, chapter 6's `ScopeProvider` made concrete) — scope resolution and placement as the core, addressing and allocation as capability flags (`provider.ts`: `{validate: true; itemAddresses; allocate; ordered}`), so a scheme whose grammar names classification tokens rather than item identities (GTD/PARA — routed elsewhere, not built here) still fits without contortion. `jd.ts` is the first (and so far only) provider — Johnny Decimal grammar ported verbatim from `obsidian-johnny-decimal`'s `jdId.ts` (areas, categories, `XX.YY`/`XX.YYY`, 5-digit expanded areas/categories, fractal ids). `registry.ts` is the `SchemeRegistry`: named instances (`{id, provider, config}` from settings, default one `jd` instance) plus address-string resolution (`jd:06.11` → path). **Config is not hardwired** (Nelson's ruling): each instance's `config` is a partial override deep-merged at the key level over that provider's own defaults, and is a **per-provider namespace validated by the provider itself** (`validateJdConfig` for `"johnny-decimal"`) — an unknown provider name or a config that fails validation **skips that one instance and logs**, rather than failing the whole registry or trusting an unvalidated shape. `findings.ts` is the pure conformance rule core (misfiled / duplicate_address / malformed_name / unaddressed, plus the name-hygiene codes `name_colon` / `name_trailing_space` folded in from obsidian-jd-numbering's `checkNote` lint — the two of its checks scheme lacked and could express purely over a filename; it bounds scheme resolution only, never general path access to the excluded notes themselves. **Three mutating tools** (`mcp/tools-scheme-write.ts`, the write half completing the module: `obsidian_assign_address`, `obsidian_refile_address`, `obsidian_renumber_address`) are thin PLAN-then-APPLY shells over a pure planning core (`kernel/scheme/mutate.ts`'s `planAssign`/`planRefile`/`planRenumber`, returning `AssignOutcome`/`RefileOutcome`/`RenumberOutcome` built from a shared `MoveStep` shape) — nothing in the tool layer recomputes "what should move where", it only decides whether to preview (`dry_run: true`, mandatory on all three, no default) or execute via `moveOne` (`tools-vault-write.ts`'s move primitive, reused rather than re-implemented, so these inherit the same link-healing `renameFile` guarantee as `obsidian_move_notes`). `obsidian_assign_address` takes `{path, scope, scheme?, dry_run}` and assigns the next free address in that scope — the same answer `obsidian_next_address` would compute for the same scope right now — and never overwrites, since planning always targets a FREE address, so a race where something now occupies the computed path fails the move rather than clobbering it. `obsidian_refile_address` takes `{path, dry_run}` with no `scope`/`scheme` argument (the note's own address, resolved against whichever configured instance recognizes it, decides both); already-correctly-filed reports `already_correct: true` with no move regardless of `dry_run`, closing the loop `obsidian_expected_location`'s `placed: false` opens. `obsidian_renumber_address` takes `{path, to_address, scheme?, dry_run, on_occupied, displace_to_address?}` and moves a note to a specific target address parsed through the resolved instance's own grammar (`provider.parse`, not a bare string guess); named `to_address`/`displace_to_address` rather than `to`/`displace_to` — `to`/`from` are well-known path-argument names in `guard.ts`'s `PATH_KEYS`, so under the original `to`/`displace_to` naming an active path allowlist checked the ADDRESS STRING as if it were a path and refused calls whose actual `path` argument was fully inside the allowlist; renaming was cheap since the tool was not yet released. `on_occupied` (`"fail"` default / `"auto"` / `"manual"`) is the explicit choice replacing what would otherwise be an interactive occupant-displacement prompt — `"fail"` refuses when `to_address` is occupied (and is a no-op success, not a "occupied" error, when the occupant IS the source note itself — a retry of an already-applied renumber), `"auto"` displaces the occupant to the next free address in ITS OWN scope, `"manual"` displaces it to a caller-supplied `displace_to_address` (parsed and required only in that branch, and refused up front if it equals `to_address`). Whenever an occupant is displaced, its move is planned and executed BEFORE the source note's own move, both in the reported `moves`/`steps` and at apply time; `dry_run: false` execution runs the steps sequentially, never in parallel, and a mid-sequence failure after at least one step has already landed returns a distinguishing error naming exactly which moves completed and which one failed, rather than a bare rethrow that would hide a partially-applied vault. All three share `tools-scheme.ts`'s allowlist discipline: `ctx.notes()` is filtered through `visiblePaths` (and, per instance, `excludeRoots`) before it reaches any provider method or planning function, and the note being operated on (`path`) gets the same one-path `out_of_allowlist` check `tools-uid.ts`'s reverse lookup uses (plus an excludedRoots-territory refusal when the selected instance doesn't speak for it), refused before planning runs — a hidden note can be neither read as "what's there" nor written to by these tools. A plan's COMPUTED destinations (`MoveStep.to`, and a displaced occupant's own path) are not call arguments, so the guard's own path check never sees them — `expectedFolder` derives a folder PREFIX from the filtered notes listing, which can be shorter than a narrower allowlist entry — so every computed path is re-checked with `isVisible` before anything is planned to happen to it, unconditionally, even under `dry_run: true`. A non-dry-run success also reports `filesChanged`/`files` in its structured result (the `reportedEffects` convention `guarded.ts` and `obsidian_repoint_link` already use), so the journal's `effects` field names every file actually touched, not just the argument-derived `target`. **They cannot register through `modules-mount.ts`**: that host's `registerAll` gate refuses any tool whose `annotations.readOnlyHint !== true` (the module host's own header comment, point 1, pinned by its own test suite) — capability modules are load-bearing read-only-or-nothing by that gate's design. The compiled output is **FLAT** (`skills/<name>/SKILL.md`, `agents/<name>.md`; `genName` derives from the note's own name, not tree position), so every emitted skill is reachable by every emitted agent through the Skill tool — the sharing property holds regardless of `parent:`. Consequences, all deliberate: **(1) `parent:` is an organizational/provenance edge and is MULTI-VALUED.** The FIRST parent is PRIMARY — the tree edge, and the only thing that drives breadcrumb, `level` (the depth-5 delegation-reachability warning), ownership and the reachability/cycle checks; single-parent notes compile byte-identically to pre-#292 **modulo the preload opt-in** (point 2 — an agent whose skills don't set `preload: true` loses the `skills:` key it used to get). The rest are recorded ATTACHMENTS: reported in `vault_skills_validate` / `_preview` (`attachments`) and on the tree nodes (`extraParents` / `attached`), with no effect on any compiled path. EVERY named parent is still validated (must resolve, must be an agent) — a dangling/non-agent extra parent is an error like the primary; a duplicate warns; an extra parent that is itself invalid is dropped with a warning rather than cascading. `type: policy` keeps STRICT single-parent on purpose (its parent is a lineage edge — a second parent would mean a second injection site). **(2) The agent `skills:` frontmatter is PRELOAD, not permission.** Per the subagent reference it "controls which skills are preloaded, not which skills the subagent can access"; unlisted skills stay invokable through the Skill tool. So it is emitted from an OPT-IN per-skill `preload: true` over that skill's attached agents (primary ∪ extra), never from attachment alone — an agent with no opted-in attachments gets NO `skills:` key (not an empty one), and attached-but-not-opted-in skills are named in the body as on-demand. The anti-pattern guard is a WARNING, never a refusal (the vault decides): `preloadCap` (config, default 5) per agent, reported by validate/preview/export with the agent and count, because preloading a scope spends the fresh context window delegation exists to provide. **(3) `no-skills: true` on an AGENT compiles `disallowedTools: [Skill]`** — the one real boundary the platform offers. `disallowedTools` (not a `tools` allowlist) is load-bearing: it is applied BEFORE `tools` resolves, so it leaves the agent's other tools alone, whereas an allowlist omitting `Skill` would also omit everything it forgot to name (an omitted `tools` inherits every subagent tool). A locked-out agent gets no `skills:` list, no Skills body section, and no structural `Skill` appended to its own `tools`; `no-skills` + opted-in attachments, and `no-skills` + a hand-written `tools: [… Skill]`, each WARN rather than being silently reconciled. Pure and headless-tested end to end (`packages/skills/tests/skills-transform.test.mjs`); the authored fields ride the module's existing `fieldMode` namespacing (`preload`, `no-skills`).
- **Fileclass module** (`src/mcp/tools-fileclass.ts`, #188) — a MUTATING capability module (mounted via `modules-mount.ts`, `enabled: false`) that PROXIES the standalone `fileclass` CLI (github.com/mdelobelle/fileclass-cli — the terminal for the Fileclass typed-frontmatter plugin), the `obsidian_cli` `execFile` precedent (chosen over calling the plugin's `app.plugins.plugins.fileclass.api` directly, which would break the module's Obsidian-free / headless-testable contract). Eight tools: six read (`fileclass_list`/`_schema`/`_explain`/`_query`/`_get`/`_validate`, `readOnlyHint: true`, `--json`) and two write (`fileclass_set` / `fileclass_set_where`, `readOnlyHint: false`; `set_where` is DRY-RUN by default, `apply: true` to commit). **Doubly gated**: the registrar registers NOTHING unless the Fileclass plugin is LOADED (`app.plugins.plugins.fileclass` — the instance, not `enabledPlugins`) AND the `fileclass` CLI binary is found (config `binaryPath`, else standard install paths) — degrades cleanly to absent. The vault is pinned (`--vault <name>`), so a session can never cross vaults. **Writes route through the accept-forbidden guard** the same way `obsidian_cli`'s `property:set` does — the write goes out through the CLI (not `ObsidianBackend`), so `acceptForbiddenReason({[field]: value})` (@vault-mcp/core, no second definition of "accepted") is applied in the tool layer BEFORE the CLI runs: a fileclass field-write can never assert `accepted`/`accepted-by`/`accepted-on` or set `acceptance-status` to accepted. This is the correct gating point #105 asks for on the fileclass field-write surface. Both write tools also ride the guard-patched registrar (read-only mode, path allowlist on the note path, queue, journal, if_rev). The whole surface REFUSES while a path allowlist is active (the CLI output can't be path-scoped — the Dataview/`obsidian_cli` precedent). Obsidian-free + headless-testable: `execFile`, the presence probe, and the binary are injected (`tests/fileclass-module.test.mjs`); only the live subprocess + plugin detection are un-headless. NOTE: the pre-existing `obsidian_fileclass_schema`/`obsidian_fileclass_insert_fields` (`tools-integrations.ts`) are for the DIFFERENT `metadata-menu` plugin and are unrelated to this module — left untouched.
- **External tool registry** (`src/mcp/external-tools.ts`): other Obsidian plugins publish MCP tools via `app.plugins.plugins['governor'].api` (`apiVersion: 1`, `registerTools`/`unregisterTools`; both `governor:ready` AND the legacy `vault-mcp:ready` workspace events fire on load during the 0.12.0 grace period). Boundary is pure data: `inputSchema` is plain JSON Schema (converted via `json-schema-to-zod.ts` — SDK `registerTool` only takes zod), handlers return plain JSON wrapped in `ok()`/`fail()`. External tools are **mutating unless `readOnlyHint: true`** (inverse of built-ins) and register through the guarded path in `buildMcpServer`, snapshot-per-connection like everything else. **A read-only claim is DISTRUSTED by default** (MEDIUM-4): believing it exempts third-party code from the queue, the journal, the allowlist, the kernel args and read-only mode all at once, on the publisher's say-so. It is believed only when the publisher's RAW plugin id is listed in the `trustedReadOnlyPlugins` setting (array, default empty, settings-tab textarea; exact match — never the sanitized form, since two ids can sanitize alike). Untrusted ⇒ registered with `readOnlyHint: false`, so read-only mode blocks it through the ordinary guard rather than a bespoke check. Read at connection-build time like the tool snapshot, so trust changes land on the next connect. The `vault-mcp-api` contract is unchanged — this is host-side policy only. Safety guards: read-only mode always applies; the path allowlist scopes recognized path-key args (path, from, to, paths, …) — mutating external tools whose args carry **no recognized path key are blocked outright when an allowlist is active** (they cannot be scoped). Publishers use the `vault-mcp-api` SDK — folded into this monorepo at `packages/vault-mcp-api` (published to npm as `vault-mcp-api`; the standalone repo is archived). **The npm package NAME stays `vault-mcp-api`** — it is a published contract with a real npm name, and renaming it would strand any consumer for zero user-visible gain (same reasoning as `@vault-mcp/core`). The SDK's host lookup is instead **dual-id**: it reads `app.plugins.plugins['governor']` first and falls back to `'vault-mcp'`, and waits on BOTH `governor:ready` and `vault-mcp:ready`, so one SDK build works against hosts on either side of the 0.12.0 grace period — mirroring the host firing both events. Its `tests/contract.test.ts` pins the SDK's shapes against this host's `external-tools.ts`, so host↔SDK drift fails a test instead of shipping.

## Build / test

- `npm run build` — esbuild, emits `main.js` (+ `bridge.mjs`). `npm test` — `pretest` builds `@vault-mcp/core`, then `tsc --noEmit && node --import tsx --test`. **The `pretest` is load-bearing, not tidiness:** since S3a the plugin's tests import several contracts (`digest`, `canonical-json`, `uuidv7`, `SessionV1`, the disposition substrate) from `@vault-mcp/core`, which resolves to `packages/core/dist` — the COMPILED output. Without the rebuild, editing `packages/core/src` and running the plugin suite tests the previous build's bytes and passes green on stale code. Do not remove it to save a few seconds.
- **The editor LSP lags** in this repo — trust `npx tsc --noEmit` (real exit code), not inline diagnostics.
- Install for testing: `cp main.js manifest.json ~/obsidian/.obsidian/plugins/governor/` then reload the plugin (or `app.plugins.disablePlugin('governor').then(()=>app.plugins.enablePlugin('governor'))` via Advanced URI eval).

## Verifying tools live (important)

Tool handlers that call `app.*` can't be unit-tested headlessly — verify against a running Obsidian by piping JSON-RPC through `node bridge.mjs --vault <name>`.

**Async handlers (anything that `await`s, e.g. `vault.read`) require keeping stdin OPEN.** If the prober's stdin EOFs, `bridge.mjs` half-closes the socket, which aborts in-flight requests *before* their async response is sent — the tool *looks* hung but isn't. Use `( printf '<json>\n…'; sleep 4 ) | node bridge.mjs …`. A real Claude Code session keeps stdin open, so this only bites ad-hoc probes.

Pure logic (`guard.ts`, `mcp/guarded.ts`, `mcp/tools-locks.ts`, `mcp/tools-uid.ts`, `mcp/tools-links.ts`, `kernel/*` except `obsidian-probe.ts`, vault-slug, socket framing, bridge selection, discovery I/O, register-command, claude-cli `findClaudeBinary`/`spawnEnv`) IS unit-tested.

**The move handlers are the one exception that IS reached headlessly.** The `obsidian` package is types-only (`"main": ""`), so a module importing `TFile` cannot load in node — `tests/obsidian-stub.mjs` registers a synchronous `node:module` resolve hook pointing the "obsidian" specifier at a stub with minimal `TFile`/`TFolder`, and `tests/link-healing.test.mjs` then `await import()`s the real handlers. It is scoped to the process that calls `installObsidianStub()`, so no other test file and no npm script changes. Use it sparingly: it exists because "a move renames link-aware" is a property of the REAL handler, not of a re-implementation. Everything else stays obsidian-free by design. The uid index's freshness is testable headlessly precisely because it is built over an injected `UidSource` — `tests/uid-index.test.mjs` drives each event type against a fake source; only the adapter (`obsidianUidSource`) and the event wiring need live verification.

## Git

Feature branch per milestone, PR to `main`, don't self-merge. Auto-review PRs you author.

**Run `./scripts/install-hooks.sh` once per clone.** It points `core.hooksPath` at `.githooks/`, enabling a `pre-commit` scan of staged content and a `commit-msg` scan of the message. Git cannot auto-install hooks, so a fresh clone is unprotected until you run it.

**NEVER paste command output into a commit message or a file without reading it first.** This is not a style rule; it is the rule that exists because it was broken. On 2026-08-27 an agent session ran a full `zsh` environment dump and pasted it into a COMMIT MESSAGE — 249 lines, 96 `NAME=value` pairs — and pushed it to this public repo. Six live credentials went out: two API keys, a GitHub OAuth token with `repo` + `workflow` scope, and three service tokens. GitHub's scanner caught it in seconds and two vendors auto-revoked; the GitHub token was still live fifteen hours later.

Three things about that are worth carrying:

- **It was in the message, not a file.** No file, tree, or branch in this repo has ever contained that text. A `.gitignore` rule could not have helped, and a hook that only scans `git diff --cached` — the obvious design, and the first thing built here — sails straight past it. That is why there are two hooks.
- **It is unfixable after the fact.** The commit reached `main` through a squash-merge, so it is in the permanent history of a public repo. Deleting a branch does nothing. Rotation is the only real remedy, which is why the hooks refuse rather than warn.
- **Half the secrets had no vendor prefix.** `NGROK_AUTHTOKEN`, `SEMGREP_APP_TOKEN` and a gateway token are invisible to GitHub's scanner — nothing recognizes their shape. `scripts/secret-scan.mjs` catches them by the NAME they are bound to, and refuses any block of 20+ `NAME=value` lines outright regardless of content, because the next dump will contain a token format nobody has a rule for.

Redact before you paste; better, do not paste environment output at all. If you need to show a variable exists, show the name.
